# Implementation Cycle

## Когда загружать

- Пользователь просит реализовать фикс, фичу, правку, рефакторинг
- Пользователь даёт задачу на изменение кода (даже однострочное)
- Пользователь описывает проблему и просит «сделай», «исправь», «реализуй»

## Цикл (5 шагов)

### Шаг 1. Коммит незакоммиченного

Перед началом новой работы проверить `git status --short`:

- Если есть незакоммиченные изменения — закоммитить их **отдельным коммитом** до начала новой работы
- Определить тип коммита по характеру изменений (см. таблицу ниже)
- Сформировать сообщение по формату Conventional Commits (см. ниже)
- **Не коммитить!** Остановиться и предложить закоммитить
- Пользователь напрямую правит дерево (`settings.py`, `.env`, код) между ходами
  агента — не полагаться на прежние чтения: затронутые файлы перечитать. При
  падении «верного» теста — сначала `git diff`: это может быть правка
  пользователя, не собственный баг.

Если незакоммиченного нет — пропустить шаг.

### Шаг 2. Очистка контекста

`ctx_reduce` — отметить spent outputs (file reads, grep results, bash outputs, предыдущие tool results) как discardable. Критерии:

- Large file reads уже использованы
- grep/search results уже проанализированы
- bash outputs уже прочитаны
- Промежуточные результаты предыдущих шагов

НЕ дропать: user messages, активные TODO, нерешённые ошибки.

### Шаг 3. Реализация

- Загрузить подходящие скилы через `skill` tool перед началом (`vk-autoliker-conventions`, `oop-design`, `testing-with-mocks` — по применимости)
- Внести изменения в код
- Обновить/добавить тест
- Актуализировать документацию проекта: бейджи, счётчики тестов, дефолты в
  README/AGENTS.md — проверять исполнением (`pytest --cov`, `settings.py`),
  не из памяти
- Прогнать `pytest -m "not browser and not live"` — все тесты должны проходить
- При правках DOM-селекторов — `-m browser`

### Шаг 4. Ревью

Загрузить `code-review` skill через `skill` tool. Провести ревью изменённых файлов по 30 критериям. Формат: Critical / Major / Minor с «почему + как исправить + пример кода».

### Шаг 5. Сообщения для комитов (без комита)

Подготовить сообщения для комитов **без выполнения комита**. Представить пользователю для подтверждения.

### Отложенный пачковый коммит

Пользователь может держать коммит («не комить», «без комитов») несколько
итераций подряд — в дереве накапливаются 2–4 логические группы из разных
задач. Когда приходит «комить»:

- Разделить накопленное на логические группы (один `type:` на группу, порядок по зависимости)
- Закоммитить всё одним заходом — без поштучных подтверждений
- Проверить `ruff check src/ tests/` + `pytest -m "not browser and not live"`
- Если группа уже была проверена в своей итерации и файлы с тех пор не менялись — повторная проверка не обязательна

## Формат комитов (Conventional Commits)

```
type: Описание с большой буквы
```

### Правила

- **Описание начинается с большой буквы**
- Описание на русском языке
- Тире `—` для уточнений: `fix: Адаптивный сбор друзей/групп — итерация по всем с safety-капом вместо среза`
- Один логический коммит — один `type:`
- Scope не используется (без `feat(scope):`)
- Несколько логических комитов — каждый со своим `type:`

### Таблица типов

| Тип | Когда использовать |
|---|---|
| `feat:` | Новая функциональность, новый параметр конфига, новая возможность |
| `fix:` | Исправление бага, некорректного поведения, ошибки |
| `docs:` | Документация (README, AGENTS.md, CONSTITUTION.md, SKILL.md) |
| `refactor:` | Рефакторинг без изменения поведения (переименование, извлечение метода, архитектура) |
| `test:` | Только тесты (новые тесты, правка тестов, тестовая инфраструктура) |

Изменения по итогам code review без изменения поведения (мёртвый код,
импорты, аннотации) — это `refactor:`, не `fix:`.

### Примеры из истории

```
feat: Рандомизация likes_per_session_min/max вместо фиксированного likes_per_session
fix: Исправления по ревью кода — JSON-decode retry, config defaults, WebDriverException break
docs: Актуализация AGENTS.md — UC, зависимости, инварианты #1/#5, новые #13-18
refactor: Pipeline для подготовки постов (CollectStage → DedupStage)
test: Тесты Pipeline, CollectStage, DedupStage + адаптация test_liker/test_post_filter
```

## Важно

- НИКОГДА не коммитить без явного разрешения пользователя
- НИКОГДА не коммитить секреты (service_token, cookies, *.db, *.log)
- `chrome_profile/`, `*.db`, `*.log` в `.gitignore` — не добавлять в индекс
- Проверять `git diff --cached` перед коммитом
