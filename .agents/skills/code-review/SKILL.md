# Code Review

## TL;DR

Читать файлы **целиком** (не diff), понять цель PR, прогнать по 30 критериям
в порядке приоритета: корректность → безопасность → тесты → архитектура →
производительность → стиль. Стиль-замечания помечать `Nit:` — не блокируют.
Формат: Critical / Major / Minor + «Хорошо» + «Итог». Если всё хорошо — так и
сказать, не выдумывать замечания ради количества.

**Не загружать, если:**
- Просят «проверь, работает ли логин/команда» — это запуск, не ревью.
- Просят «проверь, что тест зелёный» — это `testing-with-mocks`.
- Просят реализовать фикс/фичу — это `implementation-cycle`.
- Нужно исправить код, а не оценить — ревью read-only.

**Маршруты:** при ревью `src/` — загрузить `vk-autoliker-conventions`
(15 инвариантов). При ревью `CONSTITUTION.md` — `constitution`. При ревью
нового класса/сервиса — `oop-design`.

**Источники правды:** `settings.py` (дефолты), `AGENTS.md` (инварианты),
`pytest --cov` (покрытие), `tests/` (классы). Если скил расходится с
источником правды — править скил, источник не трогать.

**Версия:** 1.1.0 | **Обновлён:** 2026-10-14
- 1.1.0 — TL;DR, anti-triggers, карта маршрутов, деградированный режим, частые
  ошибки, примеры из истории, источники правды, one-liners.
- 1.0.0 — базовый набор из 30 критериев.

## Когда загружать

- Пользователь просит «code review», «ревью кода», «проверь изменения», «проверь код»
- Пользователь вставляет шаблон ревью с критериями проверки
- Пользователь просит оценить качество кода по критериям
- Пользователь присылает PR/MR для проверки
- Пользователь просит проверить изменения перед мержем или деплоем

## Процесс

1. **Прочитать все затронутые файлы целиком** — не только diff, а полный файл.
   Ревью по diff-у пропускает контекст: типы, инварианты, соглашения проекта.
2. **Понять цель изменений.** Прочитать описание PR, связанные задачи/тикеты.
   Без понимания *зачем* сделан код — невозможно оценить его *как*.
3. **Проверить по 30 критериям** (список ниже). Если изменения затрагивают
   документацию (README/AGENTS/CONSTITUTION/SKILL, докстринги, логи) или просят
   ревью доков — по чек-листу «Ревью документации».
4. **Для каждого замечания:** почему это проблема + как исправить + пример кода.
5. **Если всё хорошо — так и сказать.** Не выдумывать замечания ради количества.
6. **В конце — краткий итог и рекомендации** (см. формат ответа).

### Деградированный режим

Ревью не всегда проходит с полным бюджетом. Усечённый набор по приоритету:

- **15 минут / до 200 строк:** пп. 1–3 (корректность), 8–11 (безопасность),
  14 (наличие тестов). Остальное — вне охвата, отметить в итоге.
- **30 минут / до 400 строк:** всё выше + 4–7 (типы, качество), 18–19
  (производительность, ресурсы), 22 (архитектура).
- **Полный проход:** все 30 + чек-лист документации.

Формулировка в итоге: «Ревью в усечённом режиме, вне охвата: пп. X, Y».

### Приоритизация ревью

Не все замечания одинаково важны. Приоритет проверок:

1. **Корректность и безопасность** — баги, уязвимости, потеря данных.
2. **Архитектура и дизайн** — соответствие проекту, SOLID, границы модулей.
3. **Тесты** — покрытие, качество, граничные случаи.
4. **Производительность** — алгоритмическая сложность, N+1, утечки.
5. **Читаемость и стиль** — PEP 8, нейминг, комментарии.

Стиль-замечания помечать префиксом `Nit:` — они не блокируют мерж.

### Ограничения на объём ревью

- Не более **400–500 строк** за один проход — дальше падает концентрация.
- Сессия ревью — **не более 60–90 минут**.
- Если PR слишком большой — рекомендовать автору разбить его на части.

## 30 критериев проверки

### Корректность и логика

1. **Корректность и логика:** код делает то, что заявлено в описании; нет off-by-one, race conditions, deadlock.
2. **Граничные случаи:** пустые списки, `None`, нулевые значения, максимальные размеры, отрицательные числа, Unicode.
3. **Обработка ошибок и исключений:** нет проглоченных исключений; ошибки логируются; понятные сообщения.

### Типизация и качество кода

4. **Типизация:** аннотации, generics, `Optional`/`Union`, `TypeVar`.
5. **Стиль, форматирование:** `ruff` (lint + format), единообразие.
6. **Читаемость и поддерживаемость:** осмысленные имена, функции ≤50 строк, вложенность ≤3, отсутствие magic numbers.
7. **DRY / SOLID:** нет дублирования, каждая функция — одна ответственность.

### Безопасность

8. **Безопасность входных данных:** валидация типов, длины, формата, диапазона; allow-list вместо deny-list.
9. **Инъекции:** параметризованные SQL-запросы, нет `eval()`, нет передачи пользовательского ввода в shell.
10. **Секреты:** ключи, пароли, токены — только через env / secrets manager, не в коде.
11. **Аутентификация и авторизация:** все защищённые эндпоинты проверяют права; нет client-side-only проверок.
12. **Защита данных:** PII не логируются; ошибки не раскрывают стектрейсы; TLS для передачи.
13. **Зависимости:** новые пакеты — из надёжных источников; версии зафиксированы; нет CVE.

### Тесты

14. **Наличие тестов:** новый код покрыт тестами; бизнес-логика — обязательно.
15. **Качество тестов:** тесты детерминированы, не зависят от сети, времени, порядка запуска.
16. **Покрытие:** не снижает существующее; критичные пути покрыты; порог зафиксирован (например, 70–85%).
17. **Граничные случаи в тестах:** пустой ввод, некорректные данные, ошибки внешних сервисов.

### Производительность и ресурсы

18. **Производительность и сложность алгоритмов:** нет O(n²) на больших данных; нет N+1 запросов.
19. **Утечки памяти и работа с ресурсами:** `with`, context managers, закрытие соединений, файлов.
20. **I/O, сеть, БД, транзакции:** транзакции атомарны; таймауты заданы; retry-логика.
21. **Асинхронность и конкурентность:** нет блокирующих вызовов в async; корректная работа с `asyncio`.

### Архитектура и дизайн

22. **Архитектура, модульность, связность:** слои разделены; зависимости направлены правильно; нет циклических импортов.
23. **API-дизайн, интерфейсы, сигнатуры:** понятные сигнатуры; ≤4 параметров; нет флаговых аргументов.
24. **Зависимости, импорты:** нет неиспользуемых импортов; порядок импортов по стандарту.
25. **Мёртвый код:** нет закомментированного кода, неиспользуемых функций, устаревших веток.

### Документация и сопровождение

26. **Документация, докстринги, комментарии:** объясняют *почему*, а не *что*; API-изменения задокументированы.
27. **Логирование и мониторинг:** логи структурированы; нет чувствительных данных; уровни логирования корректны.
28. **Конфигурация и переменные окружения:** нет хардкода; значения по умолчанию задокументированы; валидация конфига.
29. **Линтеры, форматтеры, CI/CD:** код проходит линтеры; CI настроен; pre-commit hooks.
30. **Git-гигиена:** осмысленные коммиты; нет посторонних файлов; PR ограничен задачей.

## Ревью документации

Чек-лист для README, AGENTS.md, CONSTITUTION.md, SKILL.md, докстрингов и логов.

**Единый источник правды** — доки переписывают код, а не наоборот:
дефолты и имена env-переменных — из `settings.py` (`Settings.model_fields`);
счётчики тестов/покрытия — прогон `pytest --cov`; зависимости — `requirements.txt`;
список тест-классов — `tests/`; пути классов/файлов в таблицах — сверять
существованием. Не из памяти.

**Согласованность:** один и тот же факт (дефолты, счётчики, команды, инварианты)
во всех документах — одним значением; CONSTITUTION приоритетнее AGENTS, AGENTS
и SKILL не должны противоречить друг другу; бейджи = фактические.

**Докстринги:** объясняют *зачем*, не *что*; без повтора того, что видно из
сигнатуры; без деталей за пределами ответственности модуля; без контекста
предыдущих итераций («было X, исправлено», «ранее была бесконечная рекурсия»);
без исторических данных (даты «12.10», «удалено», «легаси, до m004» — допустимо
только как факт схемы, не как нарратив); без отсылок к несуществующему (классы,
атрибуты, транспорт).

**Русский язык:** докстринги, сообщения логов, все пользовательские строки
(CLI, ответы бота, метки кнопок) — на русском; технические ключи в логах
(`answer=`, `skip=`), английские слова в тексте логов (`hard/soft`,
`Unknown error`) — нет. Имена в коде остаются английскими (snake_case/PascalCase).

**Чистота аудитория:** README — без истории вообще; AGENTS/SKILL — без нарратива
о ходе фиксов, но могут хранить эмпирические основания (замеры, ограничения
API) как факты.

**Типичные находки (проверять по списку):** устаревшие отсылки к удалённым
механизмам; числа-замеры без возможности проверки («~38%») — обобщить;
расхождение одного факта между двумя доками; нумерация и счётчики в списках
(«все 46 параметров»); примеры в таблицах, противоречащие правилу.

## Формат ответа

~~~
### Critical: ...
### Major: ...
### Minor: ...

### Хорошо
Что уже сделано правильно (не только проблемы — отмечать и удачные решения).

### Итог
Краткая оценка + приоритизированные рекомендации.
~~~

- **Critical** — баг, краш, потеря данных, риск бана, пробой безопасности.
- **Major** — нарушение инварианта, архитектурная проблема, мёртвый код, десинк конфигов.
- **Minor** — стиль, дублирование, лишний импорт, PEP 8. Помечать `Nit:`.

### Формат замечания

Каждое замечание должно содержать:
- **Файл и строка:** `file.py:NN`
- **Почему это проблема:** объяснение последствий.
- **Как исправить:** конкретное предложение.
- **Пример кода:** до / после (если применимо).

## Частые ошибки агента

- **Резать по diff, не открыв файл целиком.** Теряется контекст: типы,
  инварианты, соглашения. Diff — вспомогательный инструмент, не основа ревью.
- **Выдумывать Minor ради количества.** Если всё хорошо — так и сказать.
- **Смешивать Critical и Nit в одном списке.** Стиль — всегда `Nit:` и всегда
  non-blocking.
- **Писать «надо исправить» без «почему» и «как».** Замечание без примера —
  шум.
- **Комментировать личность автора.** Только код.

## Примеры из истории

- `fix: Исправления по ревью кода — JSON-decode retry, config defaults,
  WebDriverException break` — три Major-замечания в одном PR, каждое с
  примером до/после.
- `refactor: Pipeline для подготовки постов (CollectStage → DedupStage)` —
  результат архитектурного ревью, не фикс бага.

## Проверка

```bash
pytest -m "not browser and not live" --cov=src --cov-report=term-missing -q
pytest --collect-only -q
ruff check src/ tests/
```

## Правила

- **Язык ответа — русский.** Все замечания, объяснения, примеры — на русском.
- **Примеры кода** — конкретные, с указанием файла и строки (`file.py:NN`).
- **Не предлагать коммитить** — ревью read-only, пользователь сам решает что фиксить.
- **Проверять инварианты проекта** (см. `vk-autoliker-conventions`): рандомизация пауз,
  rate-limit, селекторы, дедупликация, is_processed, безопасность аккаунта.
- **Проверять документы на соответствие фактам** (по чек-листу «Ревью документации» ниже):
  бейджи, счётчики тестов, дефолты в README/AGENTS.md сверять исполнением
  (`pytest --cov`, `settings.py`), не из памяти. Аудит неиспользуемых полей/свойств
  `Settings` (рудименты).
- **Учитывать контекст проекта**: hybrid API+Selenium, UC, SQLite, Settings (pydantic-settings).
- **Отмечать что уже хорошо** — не только проблемы, но и правильные решения.
- **Критиковать код, не автора.** Формулировки — нейтральные, конструктивные.
- **Объяснять WHY, а не только WHAT.** Предлагать альтернативы с обоснованием.
- **Указывать, блокирует ли замечание мерж** — blocking vs non-blocking.

## Принципы эффективного ревью

### Культура обратной связи

- Фокусироваться на коде, а не на личности автора.
- Использовать объективный, конструктивный, нейтральный язык.
- Задавать вопросы, а не выносить суждения: «Что произойдёт, если...?» вместо «Это неправильно».
- Отмечать хорошие решения — это укрепляет культуру.

### Ограничения и тайминги

- Первое ревью — **в течение 24 часов** (или SLA команды).
- Не блокировать прогресс без необходимости; приоритет — разблокировать других.
- Скорость ревью: **200–400 строк/час**; для сложного кода — медленнее.

### Автоматизация

- Линтеры, форматтеры, тесты — автоматизировать в CI.
- Ревьюер не должен тратить время на то, что может проверить робот.
- Использовать автоматические инструменты для: стиля (`ruff`), секретов (`gitleaks`), покрытия (`pytest --cov`).

### Малые изменения

- PR должен быть сфокусирован на одной задаче.
- Размер PR — **до 400 строк**; большие изменения разбивать.
- Малые PR быстрее ревьюятся, меньше конфликтов, легче откатывать.
