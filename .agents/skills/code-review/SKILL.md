# Code Review

## Когда загружать

- Пользователь просит «code review», «ревью кода», «проверь изменения», «проверь код»
- Пользователь вставляет шаблон ревью с критериями проверки
- Пользователь просит оценить качество кода по критериям

## Процесс

1. **Прочитать все затронутые файлы целиком** — не только diff, а полный файл.
   Ревью по diff-у пропускает контекст: типы, инварианты, соглашения проекта.
2. **Проверить по 26 критериям** (список ниже).
3. **Для каждого замечания:** почему это проблема + как исправить + пример кода.
4. **Если всё хорошо — так и сказать.** Не выдумывать замечания ради количества.
5. **В конце — краткий итог и рекомендации.**

## 26 критериев проверки

1. Корректность и логика
2. PEP 8, стиль, форматирование
3. Типизация: аннотации, mypy, generics
4. Обработка ошибок и исключений
5. Безопасность: инъекции, секреты, валидация, права
6. Производительность и сложность алгоритмов
7. Тесты: наличие, покрытие, граничные случаи
8. Граничные случаи и поведение при некорректных данных
9. Читаемость и поддерживаемость
10. Архитектура, модульность, связность
11. Зависимости, импорты, версии
12. Логирование и мониторинг
13. Конфигурация и переменные окружения
14. Асинхронность и конкурентность
15. Утечки памяти, работа с ресурсами
16. I/O, сеть, БД, транзакции
17. API-дизайн, интерфейсы, сигнатуры
18. Документация, докстринги, комментарии
19. Совместимость версий Python
20. Приватность и защита данных
21. Валидация входных данных
22. Сериализация/десериализация
23. Кэширование
24. Локализация и i18n
25. Линтеры, форматтеры, CI/CD
26. Git-гигиена (если применимо)

## Формат ответа

```
### Critical: …
### Major: …
### Minor: …

### Итог
Краткая оценка + приоритизированные рекомендации.
```

- **Critical** — баг, краш, потеря данных, риск бана, пробой безопасности.
- **Major** — нарушение инварианта, архитектурная проблема, мёртвый код, десинк конфигов.
- **Minor** — стиль, дублирование, лишний импорт, PEP 8.

## Правила

- **Язык ответа — русский.** Все замечания, объяснения, примеры — на русском.
- **Примеры кода** — конкретные, с указанием файла и строки (`file.py:NN`).
- **Не предлагать коммитить** — ревью read-only, пользователь сам решает что фиксить.
- **Проверять инварианты проекта** (см. `vk-autoliker-conventions`): рандомизация пауз,
  rate-limit, селекторы, дедупликация, is_processed, безопасность аккаунта.
- **Учитывать контекст проекта**: hybrid API+Selenium, UC, SQLite, launchd, config.yaml.
- **Отмечать что уже хорошо** — не только проблемы, но и правильные решения.
